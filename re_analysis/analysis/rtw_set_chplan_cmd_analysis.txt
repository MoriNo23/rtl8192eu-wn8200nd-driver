Function: rtw_set_chplan_cmd

**Function Purpose:**  
This inline wrapper sets the channel plan (regulatory domain / allowed channel list) for the adapter. It forwards to `_rtw_set_chplan_cmd` with a `NULL` callback, meaning it executes synchronously. The channel plan determines which 2.4/5 GHz channels, bandwidths, and transmit powers are permitted per region (country code), ensuring regulatory compliance.

**Windows vs Linux Differences:**  
- **Windows**: Channel plan is exposed via NDIS OIDs (`OID_DOT11_DESIRED_REG_DOMAIN`, `OID_DOT11_REG_DOMAINS_SUPPORT_VALUE`). The miniport processes OID sets and queries; the actual channel-to-reg-domain mapping lives in the HAL/firmware interface.  
- **Linux**: `rtw_set_chplan_cmd` is a direct driver-internal API called from `cfg80211` regulatory callbacks (`reg_notifier`, `set_wiphy_params`) or userspace (`iw reg set`).  
- The Windows binary shows **no channel-plan-specific strings**—only association, USB resource, TX power, and 8822B beamforming routines. Power management imports (`NdisMIdleNotification*`) are unrelated.  
- 8192EU is 2×2 802.11n (no beamforming), so the 8822B beamforming strings are irrelevant to this chipset.

**Backport Candidate:** **no**  

**Reason:**  
Channel-plan logic is **regulatory-driven, not performance-critical**. Both OSes must produce identical channel/power tables for a given country code. The Windows implementation is NDIS-OID-centric and tightly coupled to the Windows regulatory stack; there is no evidence of proprietary optimizations, extended channel lists, or firmware offloads in the binary strings that would benefit Linux. The Linux `cfg80211` regulatory core already provides a complete, up-to-date world regulatory database.

**Expected Impact:** none (stability/performance/features unchanged)  

**Difficulty:** low (but unjustified effort)
